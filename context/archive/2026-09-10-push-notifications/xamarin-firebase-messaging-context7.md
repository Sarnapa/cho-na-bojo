## Installation registration

### Preferred FID mode

The current Firebase Android SDK defines `register()` as its V1 registration API:

- it returns an asynchronous `Task<Void>` in Java;
- it registers the app installation with FCM;
- successful registration dispatches `FirebaseMessagingService.onRegistered(installationId)`;
- the callback value is the Firebase Installation ID (FID) to send to the application server;
- the server targets that installation using its FID-aware Admin SDK API.

FID registration must be enabled in `AndroidManifest.xml`:

```xml
<application ...>
  <meta-data
      android:name="firebase_messaging_installation_id_enabled"
      android:value="true" />
</application>
```

Expected .NET Android usage:

```csharp
await FirebaseMessaging.Instance.Register();
```

The exact binding return type may require Android task interop rather than direct `await`; verify it in the compile spike.

### FID callback

Subclass `FirebaseMessagingService` and override the registration callbacks:

```csharp
[Service(Exported = false)]
[IntentFilter(["com.google.firebase.MESSAGING_EVENT"])]
public sealed class ChoNaBojoMessagingService : FirebaseMessagingService
{
    public override void OnRegistered(string installationId)
    {
        // Persist locally, then upload through the authenticated API.
    }

    public override void OnUnregistered(string installationId)
    {
        // Remove or disable the server association when possible.
    }
}
```

This is an expected C# projection of the Context7-documented Java callbacks, not a compile-verified snippet.

### FID and token APIs are mutually exclusive

Context7 surfaced explicit guards in Firebase's implementation:

- `register()` fails with `IllegalStateException` when FID mode metadata is absent;
- deprecated `getToken()` fails with `IllegalStateException` when FID mode is enabled;
- `onRegistered()` is dispatched in FID mode;
- deprecated `onNewToken()` is dispatched in legacy token mode.

Do not combine `Register`/`OnRegistered` with `GetToken`/`OnNewToken` in one implementation. ChoNaBojo should use FID mode consistently.

### Legacy registration-token API

The following upstream APIs are deprecated:

```text
FirebaseMessaging.getToken()
FirebaseMessaging.deleteToken()
FirebaseMessagingService.onNewToken()
```

Older Xamarin and plugin examples commonly use these methods. They should not be copied into the new S-06 implementation unless a temporary fallback is required by a confirmed binding limitation.

## Automatic initialization

The Android SDK starts registration synchronization during `FirebaseMessaging` initialization when auto-init is enabled.

Relevant APIs:

```text
FirebaseMessaging.isAutoInitEnabled()
FirebaseMessaging.setAutoInitEnabled(boolean)
```

Context7's source excerpt shows this flow:

1. `FirebaseMessaging` is constructed.
2. It checks whether auto-init is enabled.
3. It calls `startSyncIfNecessary()`.
4. The SDK obtains or refreshes registration state.
5. The appropriate registration callback is dispatched.

Application implication: `OnRegistered` may occur before ChoNaBojo restores its authenticated session. The FID must therefore be saved as pending local state and uploaded after authentication becomes available.

If product consent requires registration to begin only after an explicit user action, disable auto-init and call `Register()` after consent. Context7 confirmed the control APIs but did not return the manifest keys for disabling auto-init.

## Receiving messages

### Required messaging service

Firebase requires a service that:

- extends `FirebaseMessagingService`;
- is not exported;
- handles the `com.google.firebase.MESSAGING_EVENT` intent.

Native manifest form:

```xml
<service
    android:name=".ChoNaBojoMessagingService"
    android:exported="false">
  <intent-filter>
    <action android:name="com.google.firebase.MESSAGING_EVENT" />
  </intent-filter>
</service>
```

For .NET Android, prefer generating this entry through attributes:

```csharp
[Service(Exported = false)]
[IntentFilter(["com.google.firebase.MESSAGING_EVENT"])]
public sealed class ChoNaBojoMessagingService : FirebaseMessagingService
{
}
```

Inspect the merged Android manifest to confirm the generated service entry.

### `OnMessageReceived`

Expected override:

```csharp
public override void OnMessageReceived(RemoteMessage message)
{
    IReadOnlyDictionary<string, string> data = message.Data;
    RemoteMessage.Notification? notification = message.GetNotification();

    // Validate identifiers, refresh lightweight state, and optionally
    // create a local notification while the app is foregrounded.
}
```

The property/method shapes in this example must be checked against the binding.

Context7 confirms:

- the callback runs on a worker thread;
- it should finish within 20 seconds;
- exceeding that window can interfere with current and pending work;
- a foreground notification message is delivered to this callback;
- long-running work should be handed off rather than performed inline.

Do not navigate MAUI UI directly from this service callback. Forward a small validated event into an application service and marshal UI work onto the main thread.

### Notification and data message dispatch

The Firebase Android SDK dispatches messages as follows:

| Payload | Foreground app | Background app |
|---|---|---|
| Data only | Calls `OnMessageReceived` | Calls `OnMessageReceived` |
| Notification | Calls `OnMessageReceived` | SDK displays notification |
| Notification + data | Calls `OnMessageReceived` with both | SDK displays notification; data is available through the notification intent |

The implementation checks whether the payload contains notification parameters:

1. If it is data-only, it immediately calls `onMessageReceived`.
2. If it contains notification parameters, it tries to display the notification.
3. When background display succeeds, the callback is not invoked for display handling.
4. When the app is foregrounded, automatic display falls through to `onMessageReceived`.

For S-06, notification-plus-data is suitable:

- Firebase handles background display;
- ChoNaBojo handles foreground display/state refresh;
- opaque IDs in data support authenticated navigation after a tap.

### High-priority dispatch

Context7's Firebase source excerpt distinguishes high-priority delivery from ordinary background processing:

- high-priority messages are treated as foreground broadcasts and can start the messaging service directly;
- ordinary messages on Android O and newer use a bound service under background restrictions;
- the bound delivery path has a 20-second timeout.

High priority should be limited to time-sensitive, user-visible join-request and decision notifications. It does not remove the `OnMessageReceived` execution limit.

### Deleted messages

Override:

```csharp
public override void OnDeletedMessages()
{
    // Schedule a complete refresh from the authenticated API.
}
```

This callback indicates that FCM deleted pending messages rather than delivering every individual message. The client should refetch authoritative event/request state instead of trying to reconstruct missed transitions.
